# Wisp Core Game Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Wisp lives in VIIBR as a server-wide Tamagotchi: he is fed by qualifying Suno and ViiBR tracks, grows through care, dies of neglect and hatches again as a new version, with a live status card, Mealtime feed, Billboard, Lunchbox snacks, bonds and staff controls.

**Architecture:** Game rules live in pure, Discord-free modules under `wisp/` (rules, links, life, bond, card, lines) so they are unit-tested without mocks. Storage lives in `db/` as small repositories over one aiomysql pool. Discord behavior lives in focused cogs under `cogs/` that call the pure rules and the repositories. One background loop advances time.

**Tech Stack:** Python 3.13, discord.py 2.6.4, aiomysql 0.2.0 against MariaDB 11.2 (fps.ms), pytest 9 + pytest-asyncio 1.3, black, isort, flake8, mypy.

**Spec:** `6 WISP BOT/DOCS/wisp_tamagotchi.html` (published: https://claude.ai/artifact/6mwcNS4JoKL25DFeLK1jo5). The `.md` copy beside it is out of date; the HTML wins.

**Scope:** This is plan 1 of 3. It includes the first game, Rhyme Duel. Not in this plan: more games and badges (plan 2), and everything AI: Wisp's AI voice, pickle conversations, friendship songs, song listens, Jam Space favorites (plan 3).

## Global Constraints

- Wisp is written fresh from his spec. No DJ Xo code is copied or adapted.
- Clean, professional code: no comments that narrate the next line, no duplicate helpers, no blanket `except Exception` outside the two top-level error reporters, no dead code or TODOs.
- Section headers are plain: a `# ---` rule, `# Section name`, a `# ---` rule. No emoji or decorative borders.
- Bot text: no Unicode emoji. Bullet `・`, flair `♪`, separator `・♪ ────────・──────── ♪・`. Wisp's own app emojis are allowed. No embeds.
- Slash commands only, under `/wisp` (members) and `/wispadmin` (staff = `manage_guild` permission). Guild-only: `allowed_contexts(guilds=True, dms=False, private_channels=False)` and `allowed_installs(guilds=True, users=False)`. Direct messages are ignored.
- Users are identified by Discord ID everywhere. Names are display only.
- All times are UTC. A "day" is a UTC calendar day.
- Tables use the prefix from `WISP_TABLE_PREFIX` (default `wisp_`). Tests use `wisptest_` on the real database, never a fake one.
- Errors reach staff as plain text (`Error in <context>: <Type>: <message>`), never hidden behind Wisp's personality.
- Secrets only in `.env` (already filled and verified). Channel IDs, roles and food values live in the database and are set by staff commands.
- Discord messages stay under 2,000 characters.
- Spec numbers are starting values; they live only in `wisp/rules.py`.

## Review Focus

1. **Bot was offline for hours.** Wisp must not lose care for time the bot was down. Each tick credits at most 15 minutes of elapsed time (Task 3 test `test_long_gap_only_drains_fifteen_minutes`).
2. **Two members feed him in the same second.** Both feeds count and care lands on the sum. Life updates run under a per-guild `asyncio.Lock` (Task 9 test `test_simultaneous_feeds_both_count`).
3. **One message with several links, or the same link reposted or edited in.** One feed per message (first valid link), each link counts once ever, edits are ignored (Task 2 and Task 9 tests).
4. **Track drop channel is a forum or has threads.** A post counts when its channel or its parent channel is the tracks channel (Task 9 test `test_post_in_tracks_forum_thread_counts`).
5. **Staff deletes a Wisp's Studio thread or its pinned card.** The bot recreates the missing thread or message on the next update and tells staff, instead of erroring every tick (Task 8 test `test_setup_recreates_deleted_thread`, Task 10 test `test_missing_status_message_is_reposted`).

### Task 3: Life engine

**Files:**
- Create: `wisp/life.py`, `tests/test_life.py`

**Interfaces:**
- Consumes: `wisp.rules`
- Produces: `class Phase(StrEnum): EGG, HATCHING, ALIVE, DEAD, COLD`; `class Stage(StrEnum): EGG, BABY, CHILD, TEEN, ADULT, ROCKSTAR`; `class Mood(StrEnum): HAPPY, HANGRY`; `class EventKind(StrEnum): HUNGRY, FADING, DIED, EGG_COLD, HATCH_STARTED, HATCHED, STAGE_UP`; `@dataclass(frozen=True) class Event(kind: EventKind, stage: Stage | None = None)`.
- Produces: `@dataclass class Life` with the `lives` columns as fields (`id: int | None`), and:
  - `new_egg(version: int, now: datetime) -> Life`
  - `tick(life, now, *, frozen: bool, happiness: int, caretakers: int) -> list[Event]` (mutates `life`)
  - `feed(life, meal_points: int, feeder_id: int, now) -> list[Event]`
  - `add_growth(life, points: int) -> None` (only counts while `ALIVE`)
  - `mood(life) -> Mood`, `age_days(life, now) -> int`, `is_over(life) -> bool` (`DEAD` or `COLD`)

Behavior the tests pin:
- Elapsed time per tick is `min(now - last_tick_at, MAX_CREDITED_GAP)`; frozen ticks credit nothing but still move `last_tick_at`. Credited time accumulates in `phase_seconds`, which resets on every phase change; egg warmth and hatching are measured with it, so a freeze pauses them too.
- Alive: care drains `CARE_DRAIN_PER_DAY` per 24h credited. Crossing below `HANGRY_BELOW` emits `HUNGRY` once, below `FADING_BELOW` emits `FADING` once (`warned` remembers which; feeding back above clears it). Care reaching 0 sets `DEAD`, `ended_at`, emits `DIED`.
- Feeding alive adds `meal_points` to care, capped at `CARE_MAX`.
- Egg: feeding adds to `egg_food`; reaching `EGG_FOOD_NEEDED` sets `HATCHING`, `hatch_started_at`, `hatched_by = feeder_id`, emits `HATCH_STARTED`. An egg whose `phase_seconds` reaches `EGG_WARMTH` goes `COLD` and emits `EGG_COLD`. Feeding during `HATCHING` does nothing.
- Hatching: once `phase_seconds` reaches `HATCHING_TIME` it becomes `ALIVE`, `stage = BABY`, `care = HATCHED_CARE`, `hatched_at` set, emits `HATCHED`. Hatching cannot fail.
- Stage-up on tick when age, growth and caretakers all meet `STAGE_RULES` for the next stage; emits `STAGE_UP(stage)`; `peak_stage` tracks the highest. Age counts from `hatched_at`.
- Rockstar: an Adult whose happiness stays at or above `ROCKSTAR_HAPPINESS` continuously for `ROCKSTAR_HAPPY_FOR` (tracked by `high_happiness_since`, reset when it dips).
